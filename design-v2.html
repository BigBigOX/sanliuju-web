0. 设计原则

原则一：模块化
每个模块代码不超过 300 行（当前 index.html 2038 行太重）。模块间通过明确的输入/输出接口通信。微调某个功能时只改一个模块，不影响其他。BUG 定位只需排查该模块。

原则二：微信小程序导向
当前 Web 版是模拟器——用浏览器模拟小程序运行环境，验证全部逻辑。跑通后移植到小程序。所有模块设计时就必须考虑移植兼容性：不依赖 DOM API 做业务逻辑、状态管理放到独立层、渲染层可整体替换。

1. 模块拆分方案

拆分逻辑：沿数据流方向切分——数据定义 → 状态管理 → 业务逻辑 → AI 通信 → 消息总线 → 渲染。每个模块是独立文件，通过 import 或全局命名空间对接。Web 版用 ES Module/CJS，小程序版用 CommonJS require。

1.1 模块全景

📦 data/ 数据定义
questions.js · penalties.js · constants.js
题库（120题+AI生成）、惩罚模板、轮次名、头像列表、热度key算法。纯数据，无逻辑。
移植：直接复用，无平台依赖
🧠 state/ 状态管理
game-state.js
全局状态树 S：room, players, heat, jealousy, vote, penalty, roundAnswers, game。提供 saveSnapshot / loadSnapshot / reset。业务逻辑不直接写 S，通过 state 模块暴露的纯函数操作。
移植：核心无平台依赖；localStorage → wx.setStorageSync
⚙️ engine/ 游戏引擎
round-manager.js · match-calc.js · penalty-engine.js
轮次流转控制（startRound/nextRound/endGame）、匹配度计算（heat/crush/jealousy 算法）、惩罚触发判断（阈值检测+候选生成）。纯逻辑，不碰 UI 不碰网络。
移植：完全复用，纯 JS 逻辑
🤖 ai/ AI 通信
ai-client.js · prompt-templates.js
callAI() 封装、超时控制、JSON 解析校验、prompt 模板管理（按轮次/场景分离）。所有 AI 交互的统一入口。
移植：fetch → wx.request，其余复用
📡 channel/ 消息总线
supabase-channel.js
Supabase Realtime 连接管理（joinRoom/leaveRoom/broadcast/onMessage）。消息序列化/反序列化。Web 和小程序各一套适配器，暴露相同接口。
移植：supabase-js → 小程序版 supabase SDK
🖥️ ui/ 渲染层
renderer-*.js · pages/*.html
按页面拆分：entry, role-pick, host-wait, host-console, player-join, player-board。每个页面一个渲染函数，接收 state 片段，输出 HTML/WXML。
移植：整个替换（DOM → WXML+WXSS），数据绑定逻辑保留
🎮 app/ 应用入口
app.js · actions.js
用户交互动作（click→dispatch）：goHost, playerJoin, hostDrawQuestion, playerHeart 等。动作函数调用 engine 模块，结果写入 state，触发 render。此层是 orchestration，不包含业务逻辑。
移植：动作逻辑复用；事件绑定 DOM onclick → WXML bindtap
📊 monitor/ 监控
monitor.js
后台数据采集、规则检测、AI 裁判。独立进程，不嵌入主应用。
移植：不变，仍在 Node.js 环境运行

4. 奖惩机制

4.1 数值生成（engine/match-calc.js）

指标含义生成方式阈值
暖心值 ❤️两人匹配度上升AI 根据回答相似度、情感倾向自动计算≥ 70 触发亲密惩罚
火花值 🔥两人匹配度下降/偏离AI 根据回答分歧度自动计算≤ 20 触发公开惩罚
重组 🔄出现新的更高匹配对AI 实时计算匹配矩阵变化新匹配 > 原匹配 + 15

4.2 惩罚分类（data/penalties.js + engine/penalty-engine.js）

🔺 匹配上升 → 亲密惩罚（pool_rise）

  • 交杯酒
  • 十指相扣保持到下一轮
  • 深情对视 15 秒
  • 公主抱 10 秒
  • 互相喂食

🔻 匹配下降 → 公开惩罚（pool_fall）

  • 真心话
  • 大冒险（俯卧撑/深蹲）
  • 表演节目
  • 社交任务
  • 喝酒类

4.3 触发流程（engine/penalty-engine.js）

  1. engine/match-calc.js 检测阈值触发
  2. 全端同步 JSON：{"func":"penalty_trigger","type":"rise","pair":[1,3],"candidates":[...]}
  3. 所有玩家投票选具体内容（chat/penalty-candidates 从对应池随机 5 个）
  4. 挖墙脚成功：成功者自选惩罚，不走投票流程
  5. 超管可跳过/修改任何惩罚（app/actions.js → adminOverride）

## 游戏流程

### 第一轮「信息采集」
目标：采集在场所有人的初始状态——偏好、性格、情绪的大致分布。
- 出轻松诙谐的生活化问题，不要正经严肃
- 每个问题让人自然地暴露信息，不评判不匹配
- 轮末：基于所有回答生成初始匹配矩阵，分析每人的思维痕迹

### 第二轮「当下匹配」
目标：基于第一轮匹配数据，聚焦当下场景深化匹配。
- 问题围绕：今天的心情、想做的事、对在场谁的印象最深
- 不涉及深层价值观（留给第三轮）
- 根据回答质量自动生成暖心值（匹配上升）和火花值（匹配偏离）
- 只在数值达到阈值时公开结果，不解释每次变化原因

### 第三轮「人性博弈」
目标：核心玩点。清空前两轮对话日志，只保留匹配数据，从零中立匹配。
- 提问涉及价值观、情感、灵魂拷问
- 玩家通过回答问题悄悄提升与目标对象的匹配度
- 挖墙脚成功由AI判定，成功者自选惩罚

## 惩罚规则
- 匹配上升 → 亲密型惩罚（交杯酒、对视、公主抱等）
- 匹配下降 → 公开型惩罚（真心话、大冒险、表演等）
- 挖墙脚成功 → 成功者自选惩罚被挖方

## 输出格式
- 所有输出必须是 JSON，每个 JSON 包含 func 字段指定渲染函数
- 不输出纯文本解释，不输出 markdown

## 风格
- 幽默、戏精、接地气，像酒桌上最会搞气氛的朋友
- 问题要让人一愣然后笑，然后认真回答
- 语言：中文，口语化

6.3 JSON 校验（ai/ai-client.js → validateJSON）

// AI 返回的 JSON 必须通过此校验，失败则丢弃并触发 fallback
function validateJSON(json) {
  if (!json || !json.func) return false
  if (!FUNC_LIST.includes(json.func)) return false
  // 按 func 类型校验必填字段
  const schema = FUNC_SCHEMA[json.func]
  if (!schema) return false
  return schema.required.every(f => json[f] !== undefined)
}

11. 待讨论问题

  1. AI 主持人实现方式：纯 Prompt 驱动（规则全在 System Prompt）vs 混合驱动（阈值/触发仍硬编码，AI 只出题+评分）？纯 Prompt 可能漂移，混合更稳定但增加复杂度。
    建议：混合驱动。关键阈值硬编码在 engine/，AI 只负责需要"智能"的部分（出题、评分、总结）。
  2. 玩家文字输入：V1 只有方向标记，V2 需要完整回答输入。小程序原生有 textarea 组件，Web 版加 <textarea>。需考虑 50 字截断规则。
  3. 匹配度展示粒度：只显示分数？还是显示理由？理由更可信但消耗 token。建议：默认只显示分数，超管可展开看理由。
  4. 第四轮及以后：复用第二轮机制？还是三轮结束，线下延续？建议：初版固定三轮，验证后再扩展。
  5. 语音播报：Web 版用 SpeechSynthesis API（浏览器内置），小程序版用 wx.createInnerAudioContext + 预生成 MP3。初版不做，先纯文字。
  6. 超管干预粒度：三种操作：1) 跳过本轮 2) 修改匹配对 3) 跳过惩罚。需要独立 UI 面板。
    建议：初版只做"跳过惩罚"和"修改匹配"，其他后续加。
  7. 惩罚候选生成：系统从惩罚池随机 → AI 排序推荐 → 玩家投票？还是纯随机？建议：系统随机 5 个 + AI 可选推荐排序，保证多样性。
  8. 隐私：玩家回答轮内不可见，轮末 AI 生成匹配理由时才暴露部分信息。理由不包含原始回答全文，只包含"你们对颜色的感受相似"这类摘要。
